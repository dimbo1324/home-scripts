ОБЩАЯ ОЦЕНКА
--------------------------------------------------------------------------------

Это заметно более зрелый код, чем встречается в среднем. Сильные стороны, которые
надо назвать, чтобы список ниже читался в правильном масштабе:

  - Инварианты не декларативны, а механизированы: изоляция сети проверяется гейтом,
    изоляция вебвью — capability-файлом Tauri, а не соглашением.
  - Комментарии объясняют «почему», а не «что», и в нескольких местах фиксируют
    реальные найденные баги вместе с причиной — это редкость.
  - Слоистость соблюдена: доменные крейты не знают про UI, зависимости направлены вниз.
  - `unsafe` запрещён на уровне workspace-линтов и действительно отсутствует.
  - Обработка отравления мьютексов, RAII-очистка staging, каскад отмены — сделаны
    осознанно и с обоснованием.

Тем не менее найдено 40 проблем. Часть из них — прямые расхождения между тем, что
обещано пользователю, и тем, что делает код; часть — места, где одно и то же правило
реализовано дважды и разошлось; часть — недостижимый или мёртвый код.

Главный системный дефект, который объединяет находки №2, №3, №11, №13 и №23:
**одно правило реализовано в нескольких местах, и копии разошлись.** В каждом случае
одна копия исправлена (и в комментарии написано, почему это важно), а остальные — нет.

№1. [КРИТИЧНО] README обещает то, чего продукт не делает: исходные файлы
     попадают в архив без редактирования секретов
--------------------------------------------------------------------------------

ОПИСАНИЕ
  README.md, раздел «Guarantees», утверждает дословно:
  «Secrets never reach output. Not a report, a log, the database, or an archive —
   never in the clear.»
  Это неверно применительно к архиву. Шаг 2 конвейера (`copy_project`) копирует
  отобранные файлы проекта в staging-каталог через `fs::copy` — байт в байт, без
  какого-либо редактирования. Затем staging целиком упаковывается в архив.
  `Redactor` в оркестраторе передаётся ровно в два места: `write_git_report`
  и `write_text_dump`. В `copy_project` он не передаётся вообще.

  Фактически: `03_text_dump.txt` внутри бандла отредактирован, а лежащий рядом
  оригинал `config.py`/`application.yml`/`docker-compose.yml` — нет.

  Режим `safe` отсекает файлы только ПО ИМЕНИ (`.env*`, имена с «secret»,
  «credential», «private», чувствительные суффиксы). Обычный `settings.py`
  с живым ключом внутри не попадает ни под одно из этих правил.

  Важно: сам реестр инвариантов сформулирован аккуратно — I3 перечисляет
  «лог, отчёт, историю, базу, сообщение об ошибке, буфер обмена» и НЕ упоминает
  архив. То есть неточен именно README, а не инвариант. Поведение при этом
  паритетно legacy: в архиве Python-версии (`services/copy_service.py`) вызова
  `redact_secrets` тоже нет.

  Дополнительно вводит в заблуждение docstring самой функции редактирования:
  «Applied to file content before it is included in an export or copied to the
   clipboard» — для экспорта это неправда.

  1. Немедленно (без изменения поведения): привести README в соответствие с кодом.

     Скопированные исходные файлы включаются в архив без изменений — за отбор

  3. Реализовывать редактирование потоково (по строкам), а не через

  4. Записать решение в docs/__arch__/open-questions.md: сегодня расхождение

№2. [КРИТИЧНО] Команды из package.json пишутся в три отчёта без редактирования —
     при том что четвёртый отчёт делает это правильно и объясняет почему
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Извлечение `package.json → scripts` продублировано в четырёх модулях отчётов.
  Один из них редактирует значение, три — нет:

    ЕСТЬ редактирование:
      reports/scripts.rs:86 → `out.push_str(&redact_line(&format!(...)))`
      Модульная документация там же прямо пишет:
      «a script command in particular can embed an inline credential
       (e.g. `SOME_TOKEN=abc node build.js`)».

    НЕТ редактирования:
      reports/ai_context_pack.rs:103   → пишет в `12_ai_context_pack.md`
      reports/runbook.rs:128           → пишет в `13_runbook.md`
      reports/ai_context_folder.rs:180 → пишет в `AI_CONTEXT/10_SCRIPTS.md`

  То есть риск был осознан, задокументирован и закрыт ровно в одной из четырёх копий.

  Отягчающие обстоятельства:
   - `package.json` никогда не отсекается safe-режимом: имя не чувствительное,
     суффикс `.json` не в списке исключаемых.
   - `12_ai_context_pack.md` — файл, который по собственному описанию «intended
     to be pasted into an AI assistant». То есть незащищённая копия попадает
     именно в тот артефакт, который пользователь скопирует во внешний сервис.
   - Правило зафиксировано в коде: `context/mod.rs` пишет «Every report that
     quotes raw file content ... must route the quoted text through this».
     Три отчёта это правило нарушают.

  Типичные реальные значения, которые утекут:
    "deploy": "NPM_TOKEN=npm_xxxxxxxx npm publish"
    "migrate": "DATABASE_URL=postgres://user:pass@host/db prisma migrate deploy"
    "release": "GH_TOKEN=ghp_xxxxxxxx semantic-release"

ФАЙЛЫ
  crates/codepack-reports/src/reports/ai_context_pack.rs:103
  crates/codepack-reports/src/reports/runbook.rs:128
  crates/codepack-reports/src/reports/ai_context_folder.rs:180
  (эталон корректной обработки: crates/codepack-reports/src/reports/scripts.rs:86)

К ЧЕМУ ПРИВОДИТ
  Прямое нарушение инварианта I3 и утечка учётных данных в три артефакта бандла,
  один из которых предназначен для копирования во внешнюю LLM. Уровень — тот же,
  что у №1, но здесь это уже не спорное «паритетное поведение», а несомненный
  дефект: правило записано, один вызов ему следует, три — нет.

КАК ИСПРАВИТЬ (senior+)
  Не расставлять `redact_line` в трёх местах — это воспроизведёт ту же ошибку,
  когда появится пятый отчёт. Убрать возможность ошибиться:

  1. Ввести один общий извлекатель, например в `codepack-reports/src/context/`:

       /// Скрипты из package.json. Значения УЖЕ отредактированы (I3): вызывающий
       /// не может получить сырую команду, поэтому не может её забыть отредактировать.
       pub fn package_scripts(ctx: &ReportContext<'_>) -> Vec<(String, String)>

     Возвращать отредактированные значения — единственная форма, которая делает
     ошибку невыразимой. Тип-обёртка `RedactedCommand(String)` без публичного
     конструктора из `String` усилит это ещё на уровень.
  2. Перевести все четыре отчёта на него; из `scripts.rs` при этом уйдёт
     дублирующий вызов `redact_line`.
  3. Добавить один тест на уровне конвейера: фикстура с
     `"scripts": {"deploy": "NPM_TOKEN=npm_realvalue npm publish"}`, после экспорта
     grep по ВСЕМ файлам бандла на `npm_realvalue`. Такой тест ловит и пятый отчёт,
     который ещё не написан.
  4. Заодно проверить остальные 20 отчётов, читающих файлы, тем же тестом —
     список тех, что не вызывают `redact_line`, приведён в №20.

№4. [КРИТИЧНО] action.yml: инъекция в shell через `${{ inputs.* }}` внутри `run:`
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Составное GitHub-действие подставляет все входные значения текстуально прямо
  в bash-скрипт. Выражения `${{ }}` раскрываются ДО запуска шелла, поэтому
  содержимое входа становится частью исходного текста скрипта:

      ref='${{ inputs.ref }}'                     # одинарные кавычки: ломается через '
      args=(scan "${{ inputs.project }}" ...)      # двойные: работает $(...) и `...`
      if [ "${{ inputs.history }}" = "true" ]      # то же
      args+=(--since "${{ inputs.since }}")        # то же
      args+=(--sarif "${{ inputs.sarif }}")        # то же
      echo "sarif-file=${{ inputs.sarif }}" >> "$GITHUB_OUTPUT"   # инъекция в GITHUB_OUTPUT

  Значения `project`, `since`, `ref`, `sarif` в реальных workflow часто
  подставляются из событийных данных (`github.event.pull_request.head.ref`,
  заголовок issue, имя ветки). В workflow с `pull_request_target` или
  `issue_comment` эти данные контролирует посторонний.

  Отдельно: `echo "sarif-file=..." >> $GITHUB_OUTPUT` без разделителя — перевод
  строки во входе позволяет дописать произвольные выходные переменные шага.

  Отдельно: `ref` по умолчанию `"main"`, то есть `cargo install --git ... --branch main`
  — установка с подвижной ветки. Само действие в описании просит закрепить ref,
  но значение по умолчанию этого не делает.

ФАЙЛ
  action.yml (шаги «Install codepack» и «Scan»)

К ЧЕМУ ПРИВОДИТ
  Выполнение произвольного кода на раннере с правами workflow-токена: чтение
  секретов репозитория, публикация артефактов, пуш в ветки. Классический
  GitHub Actions script injection. Для действия, которое называется
  «secret scan» и которое люди ставят именно ради безопасности, это
  особенно неприятная категория.

КАК ИСПРАВИТЬ (senior+)
  1. Ни одно `${{ }}` не должно оставаться внутри `run:`. Передавать входы
     через `env:` шага и читать их как обычные переменные оболочки:

       - name: Scan
         env:
           CODEPACK_PROJECT: ${{ inputs.project }}
           CODEPACK_FAIL_ON: ${{ inputs.fail-on }}
           CODEPACK_SINCE:   ${{ inputs.since }}
           CODEPACK_SARIF:   ${{ inputs.sarif }}
         run: |
           args=(scan "$CODEPACK_PROJECT" --fail-on "$CODEPACK_FAIL_ON")
           ...

     Тогда значение попадает в процесс как данные, а не как текст скрипта.
  2. Валидировать `fail-on` и `history` по белому списку прямо в скрипте
     (`case "$CODEPACK_FAIL_ON" in critical|high|medium|low) ;; *) exit 2 ;; esac`) —
     GitHub не проверяет `inputs` по типу.
  3. Для `GITHUB_OUTPUT` использовать heredoc-разделитель либо отклонять
     значения с переводом строки.
  4. Значение `ref` по умолчанию заменить на конкретный тег/коммит. Пока
     подписанных релизов нет (S14), закреплённый коммит — единственная
     воспроизводимая форма.

№5. [КРИТИЧНО] Гейт network-isolation обходится обычным TOML-синтаксисом
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `crates/xtask/src/network_isolation.rs` — механизм, которым, по документации,
  «инвариант I1 перестал быть текстом». Он читает манифесты собственным
  построчным парсером `declared_dependencies` (строка 135):

      if line.starts_with('[') { in_dependencies = line.contains("dependencies"); continue; }
      ...
      if let Some((name, _)) = line.split_once('=') { names.push(name) }

  Это распознаёт только форму `dep = ...`. Совершенно обычная и полностью
  валидная для cargo альтернативная запись:

      [dependencies.reqwest]
      version = "0.12"
      features = ["json"]

  парсером НЕ отлавливается: строка `[dependencies.reqwest]` начинается с `[`,
  выставляет `in_dependencies = true`, а имя `reqwest` нигде не оказывается слева
  от `=`. В список «объявленных зависимостей» вместо него попадают `version`
  и `features`.

  Тот же обход работает для `[target.'cfg(windows)'.dependencies.reqwest]`.

  Дополнительно в том же файле:
   - `"ureq"` присутствует в `NETWORK_CRATES` дважды (строки 30 и 33) — след
     копипасты в списке, который является частью механизма безопасности;
   - имя пакета берётся из имени КАТАЛОГА (`package_dir_name`), а не из
     `[package] name`; переименование каталога тихо изменит поведение проверки
     `package == ALLOWED`;
   - обходятся только `crates/*/Cargo.toml` и манифест десктопа; крейт,
     добавленный в `members` по другому пути, не проверяется вовсе.

№7. [ВЫСОКО] Распознавание «уже отредактированного» значения сделано префиксной

ОПИСАНИЕ

      API_KEY=<REDACTED>real-secret-value>

  crates/codepack-security/src/pseudonym.rs:100-107
  (последствия — в `Placeholders::value` и `Placeholders::bare`, строки 140-160)

К ЧЕМУ ПРИВОДИТ
  Обход редактирования — то есть отказ ровно того компонента, который является
  последним рубежом инварианта I3. Сценарий требует специально составленной
  строки, поэтому он редкий, но категория верная: единственная функция, решающая

       fn existing_placeholder(secret: &str) -> Option<String> {
           let c = normalise(secret);
           let ok = matches!(c.as_str(), "<REDACTED>" | "<REDACTED_SECRET>" | "<REDACTED_SECRET_LINE>")
               || is_labelled(&c, "<REDACTED:")
               || is_labelled(&c, "<REDACTED_SECRET:");
           ok.then_some(c)
       }

     «распознаётся» не смогут разойтись.
  3. Добавить property-тест: для любой строки, не являющейся точным плейсхолдером,

№17. [СРЕДНЕ] Watch-режим: throttle без trailing edge — последнее изменение серии
      теряется
--------------------------------------------------------------------------------

ОПИСАНИЕ
  Логика в watch.rs:65-72:

      if pending.is_empty() || last_emitted.elapsed() < DEBOUNCE { return; }
      last_emitted = Instant::now();
      let changed_paths = std::mem::take(&mut pending);
      app.emit(CHANGED_EVENT, ...)

  Это throttle по переднему фронту, а не debounce. Если изменение приходит

  Событие уедет только при следующем изменении, то есть, возможно, никогда.

  Ровно тот случай, который происходит постоянно: пользователь сохраняет файл,
  редактор порождает 3-4 события за 50 мс; первое отправляется, остальные
  оседают в `pending` навсегда.

ФАЙЛ
  apps/desktop/src-tauri/src/commands/watch.rs:57-73

К ЧЕМУ ПРИВОДИТ
  UI показывает устаревшее состояние проекта и не узнаёт о последних изменениях.
  Для функции, единственная задача которой — «сказать UI, что проект изменился»,
  это отказ по существу. Диагностировать такое тяжело: работает «почти всегда».

КАК ИСПРАВИТЬ (senior+)
  1. Сделать настоящий debounce с задним фронтом. Простейшая корректная форма:
     выделенный поток-агрегатор. Колбэк `notify` только кладёт пути в
     `Arc<Mutex<Vec<String>>>` и сигналит `Condvar`; поток ждёт с таймаутом

     Это устраняет и проблему «колбэк не должен делать работу».
  2. Поток-агрегатор должен завершаться при `stop_watch`/закрытии окна —

№18. [СРЕДНЕ] MCP-сервер зависает, если stdout закрылся раньше stdin
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `serve` (mcp/mod.rs:~105) поднимает `std::thread::scope`, внутри которого
  читающий поток блокируется на `input.read_line`. Если `session` завершится
  из-за ошибки записи в stdout (например, `BrokenPipe` при
  `output.write_all`/`flush`), `thread::scope` обязан дождаться читающего
  потока — а тот висит на `read_line` до закрытия stdin.

  Кроме того, `Incoming::poll` первой строкой делает `if self.closed { return None; }`,
  из-за чего уже полученная и положенная в очередь строка `notifications/cancelled`
  после закрытия ввода не будет рассмотрена — отмена в этот момент теряется.

ФАЙЛ
  crates/codepack-cli/src/mcp/mod.rs:105-125 (scope), 178-196 (poll)

К ЧЕМУ ПРИВОДИТ
  Процесс `codepack mcp`, который не завершается — висит, удерживая порт stdio
  и, возможно, временные каталоги. Клиент считает его живым.

КАК ИСПРАВИТЬ (senior+)
  1. Не использовать `thread::scope` для потока, который может блокироваться
     неограниченно. Читающий поток сделать detached (`std::thread::spawn` с
     `'static` данными — читать из `std::io::stdin()` внутри самого потока,
     а не из переданной ссылки) и завершать процесс/сессию по факту закрытия
     канала, не дожидаясь его.
  2. Либо, если тестируемость через произвольные потоки важнее (а она важна,
     сейчас `serve` тестируется на парах потоков), — оставить scope, но
     добавить общий флаг остановки: при завершении `session` выставлять его,
     а читающий поток проверять после каждого `read_line`. Это не разбудит
     заблокированный `read_line`, поэтому в дополнение сессия должна
     возвращаться немедленно при ошибке записи, а сам процесс — вызывать
     `std::process::exit` из `mcp::run` после того, как результат получен.
  3. В `poll` сначала отдавать содержимое `queued`, и только потом проверять
     `closed` — тогда отмена, пришедшая последней перед закрытием, отработает.

№22. [СРЕДНЕ] scan --history: суммарного ограничения объёма нет,
      а --max-commits 0 снимает единственное имеющееся
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `history_scan::collect` материализует каждый различный блоб на диск.
  Ограничения: `MAX_BLOB_BYTES = 8 МиБ` на блоб и `DEFAULT_MAX_COMMITS = 500`
  на число коммитов. Суммарного ограничения нет.

  500 коммитов крупного репозитория — это легко десятки тысяч различных блобов;
  при среднем размере даже в 100 КБ это гигабайты во временном каталоге.
  А `--max-commits 0` документирован как «walk all of them» и предлагается
  пользователю; `action.yml` пробрасывает его во входах. С ним верхней границы
  нет вообще.

  Комментарий в модуле прямо говорит, что кап на коммиты существует, чтобы
  пользователь «не обнаружил заполнение диска», — но кап на коммиты не
  ограничивает объём.

ФАЙЛ
  crates/codepack-cli/src/history_scan.rs:60-70, 118-260

К ЧЕМУ ПРИВОДИТ
  Заполнение диска раннера или машины разработчика документированным
  и предлагаемым использованием команды. В CI это ещё и падение задачи
  по неочевидной причине.

КАК ИСПРАВИТЬ (senior+)
  1. Ввести суммарный бюджет `MAX_TOTAL_BYTES` (например, 2 ГиБ) и счётчик
     `materialised_bytes`; при исчерпании — прекратить и выставить флаг
     `truncated_by_size`, который попадёт в отчёт и в человеческий вывод
     как ПРЕДУПРЕЖДЕНИЕ, а не примечание. Ровно ту же дисциплину
     («усечение видимо») модуль уже применяет к двум существующим лимитам,
     и её надо просто распространить на третий.
  2. Проверять свободное место перед началом (`std::fs` + platform API либо
     просто по факту ошибки записи «нет места» — отказать честно, назвав причину).
  3. Не материализовывать блоб на диск вообще: `scan_project` принимает список
     путей относительно корня, но по сути ей нужны байты. Если ввести в
     `codepack-security` вариант, принимающий `(логическое имя, &[u8])`,
     история сканируется целиком в памяти пофайлово, без временного каталога,
     и вопрос исчезает вместе с №10. Это более крупная, но и более правильная
     переделка: она же убирает материализацию в `scan --staged`.

№26. [СРЕДНЕ] codepack-ai: вся API-половина крейта недостижима ни из одного
      бинаря
--------------------------------------------------------------------------------

ОПИСАНИЕ
  `codepack-ai` объявляет `default = ["api"]`, но обе оболочки берут его как
  `codepack-ai = { path = ..., default-features = false }` (корневой Cargo.toml:138).
  Значит, в собранных бинарях отсутствуют и никем не вызываются:

    src/keys.rs      (store_key, load_key, has_key, clear_key)
    src/plan.rs      (build_plan, build_request, save_answer, SendPlan)
    src/provider.rs  (трейт AiProvider)
    src/providers/anthropic.rs (HTTP-клиент)
    lib.rs::ask      (единственная точка входа API-пути)

  Проверено поиском: единственные внешние обращения к крейту —
  `codepack_ai::handoff` из CLI и из десктопа. `ask`, `keys::*`, `plan::*`
  не вызываются нигде, включая тесты вне самого крейта.

  Это соответствует записи в ROADMAP («S13 сделано частично»), то есть
  известно. Но масштаб стоит назвать: примерно 800 строк продуктового кода
  и две тяжёлые зависимости (`ureq`, `keyring`) в `Cargo.lock`, в графе
  `cargo deny`, в поверхности аудита — при нулевой достижимости.

ФАЙЛЫ
  crates/codepack-ai/src/{keys,plan,provider}.rs, crates/codepack-ai/src/providers/
  Cargo.toml:138, 154-163

К ЧЕМУ ПРИВОДИТ
  Код, который компилируется и тестируется, но не может быть выполнен
  пользователем, деградирует незаметно: он не участвует ни в одном сквозном
  сценарии. Плюс раздутый граф зависимостей и лишний повод для advisories.

КАК ИСПРАВИТЬ (senior+)
  Это решение владельца, а не рефакторинг. Варианты, по убыванию
  предпочтительности:
  1. Довести S13 до конца: добавить команду CLI (`codepack ask`) и экран
     в GUI, включив `api` там, где это осознанно. Тогда код становится живым.
  2. Если S13 отложен надолго — вынести API-половину в отдельный крейт
     `codepack-ai-api`, не входящий в `workspace.members` по умолчанию
     (или помеченный как экспериментальный). Тогда он не тянет зависимости
     в `Cargo.lock` основного продукта и не участвует в `cargo deny`.

№28. [НИЗКО] CSP: `style-src 'unsafe-inline'` без видимой необходимости,
      нет `base-uri` и `frame-ancestors`
--------------------------------------------------------------------------------
ОПИСАНИЕ. `tauri.conf.json` задаёт
  `default-src 'self'; img-src 'self' asset: data:; style-src 'self' 'unsafe-inline';
   script-src 'self'; connect-src 'self' ipc: http://ipc.localhost`.
  Проверка фронтенда показала: `{@html}`, `innerHTML`, `eval`, инлайновых
  `style="..."` — нет ни одного. Динамические стили выражены директивой Svelte
  `style:`, которая работает через CSSOM и под CSP не подпадает. То есть
  `'unsafe-inline'` в production-сборке, вероятно, не нужен (в dev-режиме Vite
  вставляет `<style>`, там нужен). Директив `base-uri` и `frame-ancestors` нет;
  `default-src` их не покрывает.
ФАЙЛ. apps/desktop/src-tauri/tauri.conf.json
К ЧЕМУ ПРИВОДИТ. Ослабление защиты, которое ничего не даёт взамен: при появлении
  инъекции в UI разрешённые инлайновые стили — рабочий вектор эксфильтрации
  (CSS-селекторы по значению атрибутов). `base-uri` без ограничения позволяет
  подменить разрешение относительных URL внедрённым `<base>`.
КАК ИСПРАВИТЬ. Убрать `'unsafe-inline'` из production-CSP и проверить сборку
  в браузере (в проекте это уже делалось). Если dev-режим ломается — задать
  CSP по-разному для dev и release (Tauri это поддерживает). Добавить
  `base-uri 'none'; frame-ancestors 'none'; object-src 'none'`.

№29. [НИЗКО] В генерации HTML один интерполируемый параметр не экранируется
--------------------------------------------------------------------------------
ОПИСАНИЕ. `risk_item` (overview.rs:231-235) подставляет `severity` без
  `escape_html`, дважды — в значение атрибута `class` и как текст, — тогда как
  соседний `text` экранируется. Сегодня `severity` — это один из фиксированных
  литералов (`critical`/`high`/...), поэтому эксплуатируемости нет.
ФАЙЛ. crates/codepack-reports/src/reports/overview.rs:231-235 (и аналог в dashboard.rs:195-198)
К ЧЕМУ ПРИВОДИТ. Правило «экранируется каждая интерполяция» нарушено, значит
  проверить его взглядом больше нельзя. Если `severity` когда-нибудь станет
  производной от содержимого файла — это готовый XSS в отчёте, который
  открывают двойным щелчком.
КАК ИСПРАВИТЬ. Либо экранировать (одна строка), либо, что лучше, сделать
  `severity` типизированным `enum` с методом `as_class(&self) -> &'static str` —
  тогда «строка из файла» физически не сможет туда попасть, и правило держится
  типом, а не вниманием.

№30. [НИЗКО] ZIP пишется без явного включения ZIP64 и без буферизации

№31. [НИЗКО] copy_project использует fs::copy, который следует симлинкам
--------------------------------------------------------------------------------
ОПИСАНИЕ. Обход (`walk_project`) корректно исключает симлинки, но между обходом
  и копированием проходит время, а `fs::copy` разыменовывает ссылку. Классический
  TOCTOU.
ФАЙЛ. crates/codepack-engine/src/copy.rs:157
К ЧЕМУ ПРИВОДИТ. При гонке (или при экспорте активно изменяющегося дерева)

ЧТО ПРОВЕРЕНО И ОКАЗАЛОСЬ В ПОРЯДКЕ
================================================================================

Это часть отчёта, а не вежливость: она отделяет «проверено и чисто» от
«не смотрел». Ниже — то, что проверялось целенаправленно и претензий не вызвало.

  - `unsafe` отсутствует полностью; `unsafe_code = "forbid"` в workspace-линтах,
    и ВСЕ 14 манифестов действительно наследуют `[lints] workspace = true`
    (проверено пофайлово, не выборочно).
  - `unwrap()`/`expect()` вне тестов: 30 вхождений, каждое с обоснованием рядом,
    как требуют правила. Все относятся либо к компилируемым литералам regex,
    либо к предварительно заполненным картам, либо к контексту Tauri.
  - Проверка path traversal при распаковке ЧЛЕНОВ архива (`safe_member_target`)
    сделана правильно: только `Component::Normal`, две независимых проверки,
    отказ на первом же плохом члене. (Проблема не в ней, а в именах ТОМОВ — №8.)
  - Обработка отравления мьютексов: `.lock().unwrap()` не встречается нигде;
    везде `unwrap_or_else(|e| e.into_inner())` с объяснением, почему для этих
    конкретных данных восстановление корректно.
  - Экранирование HTML: `escape_html` — одна реализация на весь крейт, покрывает
    `& < > " '`, применяется на всех интерполяциях, кроме одного параметра (№29).
  - Фронтенд: ни одного `any`, `@ts-ignore`, `!`-утверждения, `{@html}`,
    `innerHTML`, `eval`, `localStorage`. Единственный канал к бэкенду —
    `lib/api/client.ts`, других импортов `@tauri-apps/api/core` нет.
  - Изоляция вебвью через capabilities: разрешены только `core:default`,
    два `dialog:*` и два `opener:*`. Файловых, shell- и HTTP-разрешений нет.
  - Инвариант I1 на уровне манифестов: обе оболочки действительно берут
    `codepack-ai` без default-features, HTTP-клиент в бинари не попадает.
    (Дефект — в самой проверке, №5, а не в текущем состоянии зависимостей.)
  - `codepack-security`: отсутствие сети, отсутствие обхода ФС, корпус-тест
    с порогами precision/recall, отдельный тест `i3_no_secret_leak` — на месте.
  - Идемпотентность редактирования плейсхолдеров восстановлена и закреплена
    тестами (кроме краевого случая №7).
  - SQL: все запросы параметризованы (`rusqlite::params!`), конкатенации нет.
    Миграции пронумерованы, транзакционны, повторный прогон — no-op.
    `foreign_keys`/`journal_mode`/`busy_timeout` применяются на каждое соединение,
    что и требуется для SQLite.
  - `scan --staged` читает индекс, а не рабочее дерево — это принципиально
    правильный выбор для pre-commit, и он обоснован в коде.
  - `codepack scan` принудительно ставит `safe_mode=full`, `diff=all`,
    `token_budget=0`, снимает лимит размера — то есть команда действительно
    отвечает на вопрос «есть ли секрет в проекте», а не «чист ли бандл».
    Это тонкое место, и оно сделано верно, с объяснением.
  - Контракт кодов возврата (0/1/2/3) вынесен в отдельный модуль, с явным

  - Дев-скрипты (`scripts/`): `shell=True` не используется нигде, argv всегда

    разделение stdout/stderr при разборе `git status` — с объяснением,
    почему их склейка была реальным багом. Логика защиты `clean-project`
    (`protection.py`) корректна, включая исправленный `lstrip("./")`.
